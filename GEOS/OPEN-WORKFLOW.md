# DESK TOP 2.0: file > open

This is the first static workflow trace for the supplied boot disk. It is an
implementation reference for the browser recreation, not a claim that the
original software has been executed or that the workflow is fully recovered.

## Evidence and scope

- Input: `GEOS Boot Disk.d64`, SHA-256
  `d71ebc7a0e9274e41d9819dd7e6cc40d52e25e34527ebbfcc459b7e6b93081e7`.
- DESK TOP class: `deskTop AM  V2.0`. Resident record loaded at `$1956`.
- Menu table `$4C64` links `open` to `$3C2F` (see `research/menu-map.json`).
- Assembly, direct-call graph, and candidate pseudocode:
  `research/open-trace/`. Generated by `ghidra/TraceOpen.java` against the saved
  `desktop-main` Ghidra project.
- Type names, API names, and directory/header offsets are interpreted using
  mist64/geos revision `617efdc7191eda14eaf699d317e66d5bda68c039`, especially
  `inc/const.inc`, `inc/jumptab.inc`, `inc/geossym.inc`, and `kernal/load/`.
- These are direct Ghidra and byte-decoding findings, not REA Evidence. The
  installed REA Windows bridge cannot import the 6502 target.

## Entry and selection

1. `$3C2F` calls `DoPreviousMenu` (`$C190`) and saves the active drive.
2. `$3C37-$3C39` checks bit 7 of `$71`; if clear, the handler returns.
   Interpreting this as the active-selection flag is supported by the selection
   cleanup at `$401C-$402D`, which clears it alongside the selected-entry state.
3. `$3C3B-$3C3F` rejects a nonzero `$78` through `$55FB`. That route displays
   **No multiple file operation for / this feature.** `$78` is used as the last
   selected-entry index, rather than an ordinary count; zero represents one
   selected entry when the selection flag is set.
4. `$3E7C` resolves selection state. `$4696` compares the selected entry's disk
   identity with the current disk; `$74` records the comparison result. The
   mismatch branch at `$3C49` uses the message at `$2E9E`, **a file from another
   disk.** Exact dialog context and all cross-disk UI behavior need runtime
   verification.
5. `$46ED` restores the selected directory pointer into `r9` (`$14/$15`) and
   reads its GEOS type byte at offset `$16`. `$3C85` copies the 30-byte directory
   entry into `$8400`, then dispatches on that type.

## Dispatch

| GEOS type | Observed route | Interpretation |
| --- | --- | --- |
| 0, 1, 2 | `$3CBE` checks DOS low nibble for PRG (2); `$551B` loads overlay 4 and calls `$5B30`, which jumps to `$6069` | Legacy program path; overlay performs additional load-address and format checks and can transfer to `ToBASIC` (`$C241`). Not every PRG is accepted. |
| 5 | `$3C9C` → `$4EE4` → `$C217` | Load a desk accessory through `LdDeskAcc`. |
| 6, 14 | `$3CA7` → `$3CD2` → `$C21D` | Load an application or auto-exec application through `LdApplic`. |
| 7 | `$3CAE` → `$3D15` | Resolve and launch the document's parent application. |
| Other types | `$3CB1` | Show **This file can't be opened / from the deskTop.**, then clean up selection. |

Consequently, fonts, printer/input drivers, and system files do not take the
ordinary application-open route in this handler. Selecting a driver through its
dedicated menu is a separate workflow.

## Opening an application

`$3CD2` prepares the environment, calls cleanup at `$3CED`, sets `r0L=0`, and
tail-jumps to `LdApplic` (`$C21D`). It pushes a synthetic return address that
resolves to `EnterDeskTop` (`$C22C`) if control returns through RTS.

The reference kernel's `load4b.s` calls `LdFile`, takes the execution vector
from the file header, and calls `StartAppl`. `load3.s` chooses record zero for a
VLIR application. These kernel semantics come from the reference source; the
kernel on this custom boot image has not been matched byte-for-byte to it.

## Opening a document

At `$3D42-$3D4D`, the code reads the selected entry's information-sector pointer
from offsets `$13/$14`. Helper `$1DE3` reads it into `$8000` using `GetBlock`.

- `$3D59` tests `$8075`, corresponding to header offset 117, the parent
  application's filename. An empty value takes the cannot-open route.
- `$3D61-$3D77` prepares that name for lookup; `$3D7A` calls `$3DAB`, which
  searches for an application and includes drive-switching and dialog paths.
- `$3D7D` recognizes error 12 (cancel). Other errors use `$259A`; failure to
  obtain an application takes the return/cleanup route.
- On the successful path, `$256B` sets `r6` to the resolved name at `$8B80`.
  `$3D98-$3DA3` sets `r0L=$80` and tail-jumps to `GetFile` (`$C208`), again
  arranging a return through `EnterDeskTop`.

The document is not treated as an independent application. The exact document
handoff contract, application matching rules, and every retry/cancel state still
need deeper tracing and runtime confirmation.

## Changes needed in the browser recreation

Before this milestone, `openFile()` dispatched on icon names; `file > open` used the first
selected file even when several are selected. Accessories are browser dialogs,
and READ ME is a special case. This does not implement the original loader.

First implementation milestone (implemented with browser applications):

1. Give files explicit GEOS type, structure, disk identity, and parent-application
   metadata. Keep display icons independent of behavior.
2. Make menu Open reject multiple selection and distinguish an unsupported file
   from a missing associated application.
3. Add an application registry and document association resolver. Initially the
   registry can launch browser implementations; binary compatibility is separate.
4. Preserve desktop selection, disk, view, and page context across application
   launch/return. Decide explicitly which parts follow observed GEOS behavior.
5. Exercise application, accessory, document, unsupported-type, missing-parent,
   and cancellation paths against the reference system before claiming parity.

Items 1–4 are now implemented in `script.js`, with automated controller and
rendered-control tests in `tests/geos-open.test.cjs`. READ ME uses the sample
TEXT READER application. Case-insensitive filename matching and restoration of
the desktop context are browser design choices. Item 5 remains unverified against
the original runtime; the tests use a DOM/canvas substitute.

## Remaining limits

Ghidra pseudocode contains warnings at external kernel calls, inline-data APIs,
and self-modifying code. Treat the assembly bytes and manually checked branch
targets as the primary evidence. No CPU execution, emulator boot, or UI
comparison was performed. Directory interpretation and API naming are
source-guided; hardware behavior and original kernel identity remain unverified.
