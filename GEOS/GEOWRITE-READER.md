# geoWrite reader evidence

## Scope

Read GEOS type 7 VLIR documents whose information-sector class is `Write Image V2.0` or `Write Image V2.1`. This reads document data in JavaScript; it does not execute geoWrite or emulate the CPU. Bold, italic, underline and the encoded point size are rendered in a selectable, scrollable read-only document region. Locally loaded GEOS font ID/size matches use original bitmap shapes and advance widths; missing matches use a browser font. Monochrome embedded pictures are decoded from referenced Photo Scrap records. Paragraph alignment, margins and first-line/hanging indentation are approximated from rulers. Pagination layout, color and editing remain outside this change.

## Decoder rules

The D64 parser retains directory start/info track-sector pointers. Opening a supported document reads its info sector and VLIR index without changing disk bytes or browser storage. Index bytes 0/1 must be 0/255; record pointers start at byte 2. A 0/255 pointer means unused; 0/0 ends the table. Records 0–60 become numbered page sections using the little-endian start-page number at info offset 137. Records 61 and 62 become separate Header and Footer sections. Reserved/image records 63–126 are never treated as text. Gaps between populated page records produce warnings.

Each text record follows linked 256-byte sectors, removing their two-byte links. The last sector contributes byte-1 minus one payload bytes, including the full 254-byte case. Bounds, repeated/overlapping sectors, overlaps with the BAM/directory/index/info sectors, invalid final lengths and non-success error-table bytes on required sectors prevent opening the document. Extraction fails as a whole instead of presenting earlier pages as a complete document.

The text decoder preserves ASCII 32–126, tab and carriage-return line breaks. A NUL ends the current record's text. A form feed becomes a visible page-break marker. It consumes 27-byte ruler escapes into paragraph metadata without exposing their payload as text. Four-byte font/style escapes update the state used for subsequent text runs: the little-endian font word has size in bits 0–5 and font ID in bits 6–15; style bits 6, 4 and 7 select bold, italic and underline respectively. Each record starts with fresh defaults and its own escapes establish the page style. Consecutive text with the same settings is grouped into a run. Plain extracted text is retained separately for export. A 5-byte graphics escape creates an image reference carrying dimensions and a VLIR record number. Its text-export representation remains a picture-omitted marker. Truncated escapes fail decoding. Other bytes become replacement characters with a warning; custom font glyph mappings and international variants are not reconstructed.

Prev/Next navigates the extracted sections. Details explains the formatting scope and lists decoding warnings. Export downloads all sections with explicit headings as UTF-8 `.txt`. Closing restores focus to the selected disk file. The original D64 Export still downloads its unchanged image bytes. Unsupported versions, geoPublish documents, programs and other native files retain the metadata-only behavior.

## Embedded monochrome pictures

The [primary geoWrite copy/paste analysis](https://www.pagetable.com/243) describes the Photo Scrap dimensions and BitmapUp compression. The local mist64/geos reference's `kernal/graph/bitmapup.s` also provides the original decoder's structure. This implementation reads the three-byte width/height header, then repeat, literal and bigcount packets. Bigcount patterns contain repeat/literal packets; nested/reserved packet codes and incomplete packets are rejected. It stops after the declared bitmap bytes, ignoring any trailing color stream, as geoWrite is monochrome. Bytes scan left-to-right and top-to-bottom; bit 7 is leftmost and a set bit is black.

The reader resolves only image records explicitly referenced by page/header/footer escapes. References must be 64–126, precede the VLIR end marker and match the Photo Scrap dimensions. Image chains use the same bounds, overlap, cycle and recorded-sector-error checks as text chains. Successful images are cached per record. A failed picture leaves the remaining document readable, displays the text placeholder and records its reason in Details. Limits are 1,048,576 pixels per image and 4,194,304 displayed picture pixels per document, counting repeated placements. Unsupported or oversized images fall back to placeholders.

The read-only DOM inserts a canvas at each successful image run between its neighboring text runs. Canvas pixel bytes explicitly set black/white and full opacity. Images preserve their aspect ratio and shrink to the available width; they are not printed at original GEOS coordinates or cropped to the original page margins. Each canvas has an image role and a dimension label. Plain-text export keeps picture-omitted markers, and the original D64 export still returns unmodified bytes.

The 26 existing Collette geoWrite documents have no picture escapes. For an independent historical bitmap, the public [geoPublish archive](https://www.zimmers.net/anonftp/pub/cbm/geos/productivity/GeoPublish_d64.zip) was downloaded locally on 2026-10-16. It decodes to a recognizable monochrome building at 216 × 144 pixels. A separately written Python expanded-stream decoder agrees with all 3,888 bitmap bytes, and a PNG made from the decoded bits was visually inspected. This verifies the bitmap data path; it is not browser rendering or native geoWrite runtime evidence.

## Paragraph alignment and indentation

The ruler record described by [the primary geoWrite format analysis](https://www.pagetable.com/242) supplies little-endian left/right margins at offsets 1/3, an absolute first-line left position at offset 21, and alignment in the low two bits of offset 23. The reader preserves ruler state across carriage-return paragraph boundaries, with fresh defaults at each page/header/footer. Text styles may change inside a paragraph without losing its ruler. Blank paragraphs are retained. Left, center, right and justified alignment map to CSS paragraph alignment; justification uses the browser's normal last-line handling.

Left/right margins are displayed as percentages of an inferred page width: 640 dots if any valid ruler right margin exceeds 480, otherwise 480. The first-line indent is `(first - left)` relative to the paragraph's usable width, which supports hanging indents when first is less than left. This inference cannot distinguish a wide page whose rulers all stay within 480 dots. Actual wrapping uses the current browser font and available viewer width; original wrapped line breaks and print pagination are not reconstructed. Ruler tabs and line spacing are supported as described below.

Coordinates require left < right <= 640 and first < right. Invalid rulers fall back to unindented left alignment and add a warning. A ruler found mid-paragraph applies at the next paragraph boundary with a warning rather than silently changing the existing paragraph. None of these display operations modifies exported text or source disk bytes. Rendered `p` elements remove the final carriage-return newline from their last displayed run to avoid adding a second visual line break; the untouched text/run model retains that newline for export. Blank paragraphs have a minimum line height.

Six additional tests cover all alignments, byte order, ruler persistence, blank paragraphs, mixed styles, invalid/misplaced rulers, proportional regular/wide-page coordinates, hanging indents, page navigation and unchanged plain-text export/storage. All 149 checks pass in this workspace. A local scan of the 26 Collette documents finds 677 left, 21 centered and 185 justified paragraphs, including 70 hanging and 85 first-line indents. Right alignment is covered by the constructed fixture. These counts are decoder observations rather than native layout validation.

## Original local bitmap fonts

**disk > load fonts** reads a local 35-track D64 without mounting it or changing the current disk. Font files must be GEOS type 8, VLIR. The header supplies the ten-bit ID at offset 128 and up to fifteen encoded ID/point-size words at offset 130. The VLIR record number is the point size. Record headers supply baseline, row byte count, pixel height and relative offsets to glyph indices/bitmap data. Printable ASCII 32–126 requires 96 monotonic bit indices (the final index gives the last glyph's end). The supplied image demonstrates why an additional index for character 127 must not be required: several fonts have an unused/nonmonotonic value there. This reader does not support that character or extended glyph maps.

Format sources are the [GEOS font analysis](https://lyonlabs.lillianskinner.ca/commodore/onrequest/geos/geos-fonts.html), [geoWrite font management](https://www.pagetable.com/238), and the local mist64/geos font-rendering source. Browser wrappers follow the primary [OpenType format specification](https://learn.microsoft.com/en-us/typography/opentype/spec/otff) and [TrueType head table reference](https://developer.apple.com/fonts/TrueType-Reference-Manual/RM06/Chap6head.html). No REA decompilation or native geoWrite execution is claimed for this change.

The decoder validates bounds, dimensions, baseline, ID/size agreement, glyph indices, sector errors, cycles and overlapping chains. Limits include 64 pixels per glyph width, a 64 KB source record, 32 imported font sizes per image, 64 registered sizes per session, 24,000 horizontal bitmap contours per generated face and a 2 MB wrapper limit. Invalid fonts produce import warnings while remaining fonts stay usable. Existing ID/size matches retain their original session face instead of being silently replaced by a conflicting font file.

Each horizontal black bitmap run becomes a rectangular TrueType contour. Font units are 64 per pixel; units-per-em equals the point size times 64. Native advance widths and baseline determine horizontal metrics and ascender/descender values. The generated font includes head, hhea, maxp, hmtx, loca, glyf, cmap, name, post and OS/2 tables with aligned offsets and checksums. `FontFace.load()` must succeed before a face is registered. Internal family names use generated identifiers, not untrusted file names. Unavailable browser font APIs, sanitizer/load failures and missing ID/size pairs leave the existing fallback working. Superseded loads and loads that finish after BASIC exit cannot register faces or reopen dialogs.

Successful faces exist only in page memory, survive disk switches/BASIC exits and disappear on refresh. Neither localStorage, web-disk JSON nor original D64 bytes change. Document text remains normal selectable DOM text with a font family applied to matching spans; font advances now influence browser wrapping. The status says GEOS fonts, mixed fonts or browser fonts, and Details lists document ID/size matches. This preserves original plain glyph shapes/widths, but browser rasterization at fractional desktop scales and synthesized bold/italic may differ from GEOS. Ruler scaling, print pagination and the unsupported style modes retain their prior limits.

The supplied `GEOWrite.d64` yields 22 sizes with no import warnings. California ID 2 supplies 10, 12, 14 and 18 points. A separate Pillow/FreeType check rasterized all 95 printable glyphs from each of the 22 generated faces: all 2,090 pixel masks and advances exactly match the source GEOS bitmaps at native integer size. This is an independent raster-engine check, not a browser FontFace/OTS or visual layout check. Run `python tests/verify-font-bitmaps.py` with Pillow installed and the local image present to reproduce it; the script creates no files. Local preview font/image artifacts under research are not committed or published.

Nine added Node checks cover source layout/metadata validation, TrueType table sizes/offsets/checksum/metrics, loading without disk changes, ID/size CSS selection, fallback and duplicate handling, bad chains/recorded errors, unavailable FontFace, asynchronous cancellation, picker behavior and the 22-size supplied-image inventory. FontFace is mocked in these controller tests. The full Node suite has 149 tests in this workspace; the source-image font check is optional elsewhere.

## Regular and decimal ruler tabs

The [primary geoWrite ruler description](https://www.pagetable.com/242) defines eight little-endian tab words at offsets 5–20. The lower fifteen bits are the position and bit 15 identifies a decimal tab. Zero positions are unused. This reader retains increasing positions, deduplicates repeated positions by keeping the first type, and warns/skips descending or out-of-range positions. Stops at/beyond the right margin are not selected for layout. Ruler state continues across paragraphs as before.

Source TAB characters become separate text runs and selectable DOM spans; exported text retains the original TABs. Once the reader is in the DOM, tab spacers are measured in sequence. Their current physical location is converted back to CSS pixels using the editor's transform scale. Ruler positions scale with the actual paragraph width, and the spacer advances to the next forward stop. For a decimal stop, the reader subtracts the width of following text up to the first period, next TAB, line break or picture. Without a period, the whole following field is right-aligned. Signs/currency prefixes are included, and style/font changes within the prefix are measured individually. Loaded original fonts use their exact glyph advances; fallback text uses canvas measurements. This is an English period-based decimal implementation, not locale-aware decimal parsing.

If no usable forward ruler stop remains, spacing advances to the next four-space boundary. A field too wide to align without backing over existing text receives a zero-width spacer. Both are explicit readability fallbacks rather than verified native GEOS edge behavior. At most 512 TABs per text record receive custom layout; later TABs retain normal browser spacing and generate a warning. Prefix look-ahead stops at the current field and does not repeatedly copy the remaining run array.

Tab spacing is measured before restoring the paragraph's alignment. Browser wrapping and center/right/justified alignment can shift or wrap fields, so those combinations remain approximate. Font loading recreates the reader and recalculates tabs. Desktop scale is normalized in the measurements; ruler coordinates themselves continue to scale to the narrow viewer. Exact native print layout is not claimed.

Eight new tests cover position/flag decoding, invalid stops, margin/width scaling, decimal-prefix arithmetic, exact native font advances, mixed-style look-ahead, preserved export/storage, transformed DOM geometry/alignment restoration, layout limits and historical inputs. Seven are synthetic/controller tests; the historical check is optional on other checkouts. All 149 Node tests pass locally. ## Ruler line spacing

The [primary geoWrite ruler description](https://www.pagetable.com/242) assigns bits 2–3 of ruler byte 23 to single (0), 1½ (1), and double (2) spacing. The reader preserves alignment in bits 0–1 and carries spacing across paragraphs until the next ruler. Each text record (page/header/footer) starts with single spacing. Reserved value 3 falls back to single and adds a ruler warning; invalid geometry resets the entire ruler. A mid-paragraph ruler applies at the next paragraph boundary with the existing warning.

Paragraphs use unitless CSS line heights of 1, 1.5 or 2, so mixed-size text contributes its own font metrics. Blank paragraphs receive a minimum height based on their active font size and spacing. Browser baselines, wrapping and synthesized styles remain approximations of native GEOS. Text export, source D64 bytes and web-disk storage are unchanged.

Five new controller/decoder checks cover spacing/alignment independence, reserved values, persistence and invalid/misplaced rulers, mixed fonts and blank paragraphs, section resets/navigation and unchanged export/storage/bytes. ## Superscript and subscript

The [primary geoWrite format description](https://www.pagetable.com/242) defines superscript as style bit 2 and subscript as bit 1, and disallows their combination. The decoder keeps the original style byte and point size. The viewer renders either script at 75% of the encoded size, using the original ID/size font face when loaded (scaled in the browser). Superscript moves up 0.35 of its rendered em, subscript down 0.2 em. These sizes/offsets are explicit browser approximations, not measurements of native GEOS. Existing bold, italic and underline can combine with scripts. Both script bits together retain normal size/baseline and add a decoding warning.

Relative positioning with a zero-height inline line box leaves ruler line spacing controlled by the paragraph's unscaled font strut and ordinary text. No extra characters are inserted: x plus a scripted 2 exports as x2, and H plus a subscript 2 plus O exports as H2O. Native font advances and fallback measurements receive the same 75% scaling for decimal-tab prefixes and fallback tab widths. Original source bytes and disk storage remain unchanged.

## Reverse text

The [primary geoWrite format description](https://www.pagetable.com/242) defines reverse as style bit 5 ($20). Text runs with this bit use light (#eeeeee) letters on a dark (#111111) background; normal runs use dark letters and a transparent background. The inline background covers text and ordinary spaces, follows browser wrapping, and ends with the styled run. Bold, italic, underline and script positioning remain independent. Font ID/size matching, glyph advances and tab measurements do not change. Custom tab spacers remain unpainted, and pictures are unaffected.

This is a CSS approximation of reverse text, not native GEOS pixel inversion: background bounds, line metrics, rasterization and selection appearance depend on the browser. No text or markup is added to exports, source D64 bytes or web-disk storage.

## Outline text and style acceptance

The [primary geoWrite format description](https://www.pagetable.com/242) defines outline as style bit 3 ($08). Outline runs receive a browser text stroke of 0.08 em in their foreground color, with their interiors filled using the page color. Reverse-outline runs use light strokes with dark interiors on the reverse background. Existing bold, italic, underline, superscript and subscript remain independent. No extra padding, characters or advance widths are added; tab spacing, source point-size matching and original-font family selection are unchanged.

The CSS is guarded by text-stroke feature support. Browsers without it retain solid readable text. Selected outline text uses the browser selection foreground without a stroke. Stroke edges, small-size legibility, underline positioning and combined-style rasterization remain browser approximations; the implementation does not reproduce the native GEOS outline bitmap algorithm. Custom TAB spacers and pictures remain unaffected.

## Headers and footers within pages

The [primary geoWrite document format description](https://www.pagetable.com/242) defines the title-page flag as bit 7 of info-sector byte 139 ($8B). The reader now exposes that flag and composes each numbered page as header, body, footer using records 61 and 62. When the flag is set, record 0 omits the repeated header and footer regardless of the displayed start-page number. NLQ bit 6 does not trigger title-page suppression. If record 0 is missing, a later surviving page still displays its header/footer.

Repeated sections use the same styled paragraph, original-font, tab and monochrome-picture renderer as body text, with independent decoded formatting state. Missing sections create no placeholder. Header/Footer entries remain independently navigable after the numbered pages, including for a one-page title document. Accessible regions identify the repeated sections. Font status counts the currently visible header/body/footer runs. Plain-text Export retains each original section once rather than duplicating repeated headers/footers for every page.

Sections flow above/below body text in the scrollable viewer with a small dotted separator. This is a page composition preview: cached header/footer heights, fixed paper height, footer placement at the physical bottom, title-page print geometry, NLQ printer metrics and repagination are not implemented. Existing wrapping and style rasterization limits remain. Source disk bytes and localStorage are unchanged.
